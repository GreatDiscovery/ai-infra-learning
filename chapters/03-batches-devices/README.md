# 03 · batch 与设备：同一个模型怎样跑

先完成第 01–02 章。本章关注模型前向推理，不训练参数；这样 batch 改变后不会同时改变优化器更新次数。

## 运行

```bash
python run.py 03
```

无需下载数据和权重。使用同一个随机初始化分类器、512 张随机图片，对比 batch=1、16、64、256。默认 CPU 加可用 GPU；没有 GPU 也可以运行。

每种配置的所有输出都会与同一 CPU 参考结果比较。随机图片和未训练模型用于性能实验，输出不能当成有效的分类预测。

## 先看两个控制变量

- **batch size**：样本总数保持 512，只改变每次前向处理多少张。batch 越小，前向调用次数越多。
- **输入放置方式**：`per_batch` 在计时内将每一批送到设备；`resident` 在计时前已把全部输入放到设备。

两种方式都计入前向、拼接全部输出与完成同步，不计模型初始化、随机数据生成、结果复制回 CPU。resident 的完整输入预先占用设备内存；本例只用小数据，不代表真实服务能把所有输入都预先放进去。

CPU 上同类型 CPU Tensor 调用 `.to('cpu')` 通常不复制；因此 CPU 两种模式的耗时差不能直接解释成“搬运速度”。Apple 的统一内存也不代表不同后端的分配、复制和同步开销自动为零。

## 报告怎么读

输出在 `results/03-batches-devices/时间戳/`，有中文报告与原始计时。每种方式预热 3 次，重复 5 次取中位数，两种模式交替先后顺序。设备和 batch 顺序仍固定，严谨比较应多轮复测。

- **完成整组 ms**：处理全部指定样本并等待完成的墙钟时间。
- **张/s**：样本总数除以完成时间，代表这个离线工作负载的吞吐。
- **前向调用数**：样本数除以 batch size 后向上取整，最后一批可以不足一个完整 batch。

不能把“整组耗时/样本数”当成线上单个用户等待时间。这个程序没有请求到达、凑批等待、排队和网络回传。

## 动手顺序

1. 默认运行，固定设备，找 batch=1 与 batch=64 的调用数和吞吐。
2. 固定 batch，比较 CPU/GPU；GPU 是否总更快？先检查小任务的调度和同步成本。
3. 固定设备及 batch，比较输入模式。出现差异只是线索，还需要 profiler 验证来源。

```bash
python run.py 03 --device cpu --batches 1 64
python run.py 03 --device mps --batches 16 64 256
python run.py 03 --samples 513 --batches 64 --repeats 3
```

最后一条专门观察不足完整 batch 的尾批：513 张应该产生 9 次调用。

## 面试问答

<details><summary>吞吐和延迟有什么区别？</summary>

吞吐是单位时间完成的工作量；延迟是指定任务从开始到完成的时间。批处理可能改善吞吐，也可能增加请求等待时间，先说明测量边界。
</details>

<details><summary>为什么这里不一边训练一边比较 batch？</summary>

相同 epoch 下改变训练 batch，会改变参数更新次数及梯度统计，进而影响学习过程。本章先固定模型，只研究推理的系统行为。
</details>

<details><summary>GPU 比 CPU 慢，就说明 GPU 没用吗？</summary>

不能。小任务可能难以抵消调度、搬运与同步成本；不同形状、规模、精度、后端会改变结果，需要针对实际工作负载测量。
</details>
